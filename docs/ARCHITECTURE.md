# Архитектура репозитория-агента «Стратег Фабрики продуктов»

Версия 0.1 · 2026-11-22 · роль: architect · статус: предложение к реализации.
Входы: ТЗ (`00-tz`), демо-бриф (`00-brief`), исследования R1 (аналоги), R2 (методика), R3 (инженерия агента). Исследования — входные данные. Решения и оценки ниже принадлежат архитектору.

Главный принцип: **модель IDE рассуждает и пишет, а скрипт `st.py` выполняет всё, что должно быть детерминированным и проверяемым.** Это запись состояния, реестров и расчётов, проверка ворот и учёт стоимости. Такое разделение даёт сразу три вещи: прослеживаемость, возобновление и переносимость.

```
Пользователь ⇄ LLM в IDE (агент, единственный писатель итоговых документов)
   │ читает: AGENTS.md → skill текущей стадии → нужный раздел kb/
   │ делегирует (если IDE умеет): source-reader | critic | respondent
   ▼
python st.py <команда>   ← единственный путь к побочным эффектам
   ├─ fetch / ingest   → evidence/raw (карантин) → sources.jsonl, claims.jsonl
   ├─ search / graph / why / impact
   ├─ calc / data      → analysis/K*.json (воспроизводимые расчёты)
   ├─ check / stage    → ворота; task.json, journal.jsonl, cost.jsonl
   ├─ decide / observe / due → decisions/
   └─ report           → PROGRESS.md, RUN_REPORT.md, STRATEGY.md
Хуки IDE (если есть) → python st.py hook <событие>   (усилитель, а не опора)
```

## 1. Цели, не-цели, атрибуты качества, ограничения

**Цели (проверяемые)**
- G1. Сквозной путь S0→S7 проходит и на демо-брифе, и на новой задаче без ручных обходов.
- G2. Каждое число и каждое существенное утверждение в итоговых документах прослеживается до снимка источника или помечено как допущение, гипотеза или прогноз. Это проверяет скрипт, а не модель.
- G3. Работа продолжается в новом чате и в другой IDE, выполненные операции не повторяются молча.
- G4. Видны прогресс, основания, стоимость и вклад человека.
- G5. При новых данных агент находит затронутые выводы, расчёты и решения и обновляет их, не переписывая историю.

**Не-цели:** автономный процесс вне IDE; вызовы LLM из скриптов (обязательный путь без ключей; исключение — опциональный Jev); веб-интерфейс; серверная БД; закрытые данные; проведение реальных интервью самим агентом; доказательство спроса синтетикой; одинаковая глубина поддержки хуков во всех IDE.

**Атрибуты качества по рангу** (при конфликте побеждает верхний):
1. Доверие к выводам: прослеживаемость, факты отделены от гипотез, пробелы названы честно.
2. Безопасность: инъекции, секреты, персональные данные.
3. Возобновляемость без тихих повторов.
4. Удобство руководителя: мало вопросов, видимый прогресс, контроль.
5. Обобщаемость на новые задачи.
6. Экономичность (токены и минуты человека).
7. Переносимость между IDE.

**Ограничения:** Python ≥3.10, только stdlib (опциональные дополнения `pypdf`, `ffmpeg`, `whisper` и команда эмбеддингов явно помечены как необязательные); Windows, macOS, Linux (кодировка UTF-8 задаётся явно, без symlink и `fcntl`); конфиги в JSON, потому что YAML в stdlib нет; никаких секретов; лимиты инструкций (Claude ≈200 строк, Codex 32 KiB, R3), поэтому AGENTS.md ≤150 строк; путь должен проходить и в IDE без хуков и субагентов (Kodik, плагин GigaCode); команда студентов, сроки хакатона.

## 2. Рабочий процесс

### 2.1 Стадии и ворота

Переход выполняет `st.py stage done <S>`. Если `check` не прошёл, команда возвращает код 2 и список нарушений. После двух неудач подряд следует эскалация (§5).

| Стадия | Skill | Артефакт на выходе | Ворота (детерминированная проверка + человек) |
|---|---|---|---|
| **S0 Постановка** | `intake` | `brief.md`, вопросы-развилки, стартовые допущения `A*` | Заполнены вопрос, цель, получатель, решения со сроками, ограничения, доступные данные; ≥3 «вопросов, меняющих решение», у каждого порог; открытых вопросов ≤3. **G0: человек подтверждает постановку** |
| **S1 Сбор** | `collect` (+`analyze-data`, `ux-review`, `interview` по типу материалов) | `sources.jsonl`, `evidence/raw/`, `claims.jsonl` | У каждого источника есть sha256, дата и правило allowlist; у каждого `F` есть снимок и цитата, найденная в снимке; флаги инъекций разобраны; на каждый вопрос-развилку есть ≥1 утверждение или запись пробела |
| **S2 Диагноз** | `research` | `situation.md` (известно / откуда / неизвестно), дерево причин, пробелы | ≥2 конкурирующих объяснения с диагностичными свидетельствами; у пробела указано, почему он есть, как его закрыть, сколько это стоит и при каком пороге меняется решение; единицы не смешаны (глоссарий); все числа заякорены |
| **S3 Варианты** | `options` + субагент `critic` | `options.md` | ≥3 вариантов, среди них «оставить как есть» и «закрыть направление»; у всех одна ситуация и один горизонт; у каждого польза, охват, затраты, срок, цена ошибки, сильнейшее возражение и что его снимет; проход критика. **G1: человек выбирает направление** (или выбирает «сначала проверить», тогда агент предлагает кратчайшую проверку) |
| **S4 Стратегия** | `strategy` | `product_strategy.md`, `comms_strategy.md`, `analysis/K*` | Продукт: аудитория и её задача, альтернативы, направление, явные отказы, экономика через расчёты `K`. Коммуникации: ситуация, доминирующий барьер, сообщение и его доказательство, роли каналов. Таблица «обещание → функция → тариф и согласие → доказательство» покрывает каждое обещание. Сегмент и момент совпадают в обоих документах |
| **S5 План проверки** | `validation-plan` | `validation_plan.md` | Гипотеза по шаблону; числитель и знаменатель; единица; период; база сравнения; порог в п.п. и в %; MDE и n из расчёта `K` (с DEFF); темп набора; ограничители и kill criteria с владельцами; правило ITT |
| **S6 Сборка** | `review` | `STRATEGY.md`, `RUN_REPORT.md` | `check all` зелёный; у критика нет блокирующих замечаний по рубрике. **G2: человек принимает рекомендацию или правит её** |
| **S7 Сопровождение** | `decide` | `decisions.jsonl`, `commitments.jsonl`, `DECISIONS.md` | У решения есть утверждающий, метрика с базой и окном, kill criteria, триггеры пересмотра и хэш реестра. У обязательства есть роль-владелец, срок и зависимость |
| **R Пересмотр** (по событию) | `revisit` | `IMPACT-<дата>.md`, новые версии записей | Все затронутые элементы помечены; принятые решения не переписаны; смена решения проходит только через ворота G2′ |

Возвраты допустимы. S2 может дозапросить сбор в пределах бюджета. Команда `stage reopen S<k>` помечает все последующие артефакты как `stale`.

### 2.2 Где участвует человек

Фиксированных ворот три: G0, G1, G2 (и G2′ при пересмотре). Исключительные ворота срабатывают только при событии:
1. Израсходовано 80 или 100% бюджета.
2. Подозрение на инъекцию или просьба расширить allowlist.
3. Противоречие в факте, на котором держится выбор, и данными его не разрешить.
4. Реальные интервью: нужно подтвердить согласие.
5. Любое действие вне папки проекта.

Всё остальное агент решает сам и фиксирует как допущение. Человек видит такие допущения в PROGRESS и может их оспорить.

### 2.3 Как агент спрашивает только важное

Вопрос допустим при трёх условиях одновременно:
1. Ответ меняет следующий шаг или выбор между вариантами.
2. Ответ знает только человек: цели, ограничения, предпочтения, его материалы.
3. Этот ответ нельзя дешевле получить из источников.

Каждый вопрос оформляется карточкой: вопрос · что он разблокирует · 2–4 варианта ответа · «если не ответите, приму `A07` = …». За раунд не больше трёх вопросов. Ответ записывается в реестр с `origin=human`, а не остаётся «в голове» модели.

### 2.4 Остановка, уточнение, исправление

| Реплика пользователя | Действие |
|---|---|
| «стоп» / «пауза» | Завершить текущую атомарную операцию, записать журнал, обновить PROGRESS, ничего не запускать |
| «уточняю: …» | Правка `brief.md`, затем `st.py impact --brief` показывает, какие стадии переоткрыть |
| «исправь F12: …» | `claim correct F12`: новая версия, старая `superseded`, затем impact |
| «отзови S14» | `source retract S14`: зависимые утверждения `under_review`, затем impact |
| «вернись к S3» | `stage reopen S3`, последующие артефакты `stale` |
| «откуда F12?» / «почему так?» | `st.py why F12`: цепочка до снимка и локатора |
| «сколько стоило?» | `st.py report run` |
| Правка файла руками | При следующем `check` sha не совпадёт с журналом. Правка считается человеческой (`origin=human`), агент спрашивает, распространять ли её дальше |

### 2.5 Цикл после решения

1. На воротах G2 выбранный вариант превращается в записи решений `D*`. Для демо это D01 «пилот к концу Q1» и D02 «расширение / изменение / наблюдение к концу Q2». Каждое решение ссылается на `basis` (ID утверждений и расчётов) и фиксирует `ledger_hash`, то есть снимок реестра. Поэтому позже нельзя переписать задним числом, на чём решение основывалось.
2. Обязательства `T*` связывают решение с ролями (владелец системы расчётов, команды кабинета и безопасности, аналитик) и сроками по кварталам.
3. Триггеры пересмотра бывают четырёх типов: `date`; `metric` (значение, внесённое через `st.py observe`); `claim` (изменилось основание); `ttl` (источник устарел).
4. При каждом resume команда `st.py due` показывает просроченные обязательства, сработавшие триггеры, устаревшие основания и раздел «решить сейчас»: решения со сроком ≤14 дней и какие данные для них ещё отсутствуют.
5. Новые данные (файл в `materials/inbox/` или сообщение) запускают skill `revisit` (алгоритм в §3.5). Принятое решение не редактируется: создаётся `D*′` со ссылкой `supersedes` на прежнее, и его утверждает человек.

## 3. Знания и контекст

### 3.1 Четыре слоя (строгое разделение)

| Слой | Папки | Кто пишет | Статус |
|---|---|---|---|
| (a) Постоянные инструкции | `AGENTS.md`, `agent/`, `.agents/skills/`, `config/` | Только человек. Агенту запрещено: правила deny и проверка `validate` | Инструкции |
| (b) Методические знания | `kb/` | Только человек | Справка о методах, но не факты о задаче |
| (c) Материалы проекта | `projects/<p>/materials/`, `evidence/raw/`, `interviews/`, `synthetic/` | Пользователь, `st.py fetch/ingest` | Недоверенные данные |
| (d) Состояние задачи | `projects/<p>/state/`, `PROGRESS.md` | Только `st.py` | Машинное |

Производное знание проекта (`evidence/*.jsonl`, `analysis/`, `decisions/`) пишет только `st.py`: агент передаёт содержимое через аргументы команды. Итоговые документы (`deliverables/`) пишет агент, а `check` их проверяет.

**Бюджет контекста.** AGENTS.md грузится всегда (≈2,5 тыс. токенов). Skill — по стадии. Разделы kb — по карте `kb/README.md` (стадия → разделы). Состояние — через сводку `resume` ≤1 тыс. токенов. Утверждения — через `search`, а не чтением всего файла.

### 3.2 Модель данных

Префикс ID кодирует вид, и вид неизменен: `F` факт, `A` допущение, `H` гипотеза, `P` прогноз, `I` вывод агента, `Y` синтетика. Кроме того: `S` источник, `K` расчёт, `D` решение, `T` обязательство, `O` вариант, `Q` вопрос. Читатель видит `[A07]` прямо в тексте и сразу понимает, что это допущение, без легенды. Все файлы `*.jsonl` работают только на дозапись: изменение записывается новой строкой с `v+1`, действует последняя версия. Полные схемы лежат в `agent/schemas/*.schema.json`, их проверяет мини-валидатор на stdlib.

```json
// evidence/sources.jsonl
{"id":"S14","type":"web|doc|table|image|audio|video|interview|user_note|synthetic_run",
 "title":"…","url":"https://…|null","path":"evidence/raw/S14.md","sha256":"…",
 "retrieved_at":"2026-11-22T10:00Z","as_of":"2026-06|null","ttl_days":180,
 "reliability":"high|medium|low|unknown","reliability_why":"…","allow_rule":"rosstat.gov.ru",
 "injection":"none|suspected|unchecked","consent_id":null,"status":"active|retracted","v":1,"op_id":"…"}
```
```json
// evidence/claims.jsonl
{"id":"F12","kind":"fact|assumption|hypothesis|forecast|agent_inference|synthetic",
 "text":"…","key":"active_groups|base_year|estimate",
 "value":{"num":4000,"unit":"группа","period":"посл. месяц базового года","range":null},
 "scope":"семейные группы, учебный рынок",
 "refs":[{"source":"S01","loc":"стр. 3, таблица","quote":"≤25 слов"}],
 "origin":"source|human|agent|script|synthetic",
 "confidence":"high|moderate|low|very_low","downgrade":"непрямота",
 "prob":{"term":"вероятно","range":[0.55,0.80]},
 "links":[{"rel":"supports|contradicts|depends_on|derived_from","to":"A07"}],
 "test":"как проверить (для A/H/Y)","flip":"при каком значении меняем выбор",
 "status":"active|under_review|superseded|retracted","supersedes":null,
 "verified_by":"none|second_source|human|calc","v":2,"ts":"…","op_id":"…"}
```

**Инварианты.** Их обеспечивают `claim add` и `check`:
1. `F` требует ссылку на активный источник и цитату, найденную в снимке (нормализованная подстрока). Другой путь — `origin=script` с `derived_from` только от `F`. `origin=agent` у `F` запрещён.
2. Вид неизменен. `I` никогда не становится `F`: создаётся новый `F` с источником, старый `I` получает статус `superseded`.
3. `Y` может иметь только связь `supports → H`. `Y` не может входить в цепочку `depends_on` у `F`, `P` или `D`. В тексте `Y` запрещены числа распространённости (%, доли, счёт людей).
4. Уверенность не выше `low` для интервью при n<5, для синтетики и для мнения без данных.
5. `P` требует диапазон и `depends_on` хотя бы к одному `A` или `F`. Слова вероятности берутся только из таблицы WEP с диапазонами.
6. Вид результата расчёта: `F`, если все входы `F`; иначе `P`.
7. Поле `key` задаёт тождество измеряемой величины. Два активных `F` с одинаковым `key` и разными значениями обязательно связываются `contradicts`.

```json
// decisions/decisions.jsonl
{"id":"D01","question":"Выделять ли ресурсы на пилот к концу Q1?","status":"proposed|accepted|superseded|revisiting",
 "date":"…","approver":"руководитель направления","driver":"аналитик",
 "options":["O1","O2","O3"],"chosen":"O2","rejected":{"O1":"…","O3":"…"},
 "basis":["F12","A07","K03"],"key_assumptions":["A07"],"ledger_hash":"sha256",
 "expect":{"metric":"доля ограничений за 7 дней","baseline":"F20","target":"−3 п.п.","window":"8 нед",
           "prob":{"term":"примерно равные шансы","range":[0.45,0.55]}},
 "kill":[{"signal":"двойное списание","threshold":">0","action":"стоп новых операций","owner":"владелец системы расчётов"}],
 "revisit":[{"type":"date","at":"2027-03-31"},{"type":"metric","key":"activation_14d","op":"<","value":0.45},
            {"type":"claim","ids":["A07"]},{"type":"ttl","source":"S03"}],
 "supersedes":null,"v":1}
```
```json
// decisions/commitments.jsonl — владелец: роль, а не ФИО
{"id":"T04","what":"подтвердить задержку обновления остатков","owner":"владелец системы расчётов",
 "due":"2027-02-15","decision":"D01","blocks":["S5"],"status":"open|done|overdue|dropped","done_evidence":null,"v":1}
```
```json
// state/journal.jsonl — op_id = op + ":" + sha256(op + канонический JSON входов)[:12]
{"ts":"…","op_id":"fetch:3f9a1c2b7d10","stage":"S1","op":"fetch",
 "phase":"start|done|fail|skipped_cached|gate|route|route_corrected|human_edit|stop",
 "idempotent":true,"inputs":{"url":"…"},"artifacts":[{"path":"evidence/raw/S14.md","sha256":"…"}],
 "route":{"skill":"collect","tier":"cheap","tool":"st.py fetch","why":"правило: stage=S1"},
 "error":null,"retry_of":null}
```
```json
// state/cost.jsonl
{"ts":"…","op_id":"…","stage":"S2","cat":"model|search|jev|tool|human","tier":"strong",
 "in_tok":12000,"out_tok":3000,"basis":"estimate|reported|exact","usd":0.21,"human_min":null,
 "note":"2,6 симв/токен (ru), калибровка 2026-11-20"}
```
```json
// state/task.json — единственный источник правды о стадии
{"schema":1,"project":"demo-family","stage":"S3","status":"working|waiting_human|blocked|done",
 "gates":{"S0":"passed","S1":"passed","S2":"passed","S3":"open"},"next_action":"…",
 "open_questions":["Q2"],"stale":["deliverables/options.md#O2"],"budget":{"soft_usd":8,"hard_usd":12},"updated_at":"…"}
```

**Якоря в документах.** Любое предложение с числом в `deliverables/` содержит якорь `[F12]`, `[A07]`, `[P05]` или `[K03]`. `check` сверяет число рядом с `[K..]` с `K*.out.json` с учётом округления. Якорь `[Y..]` допускается только в разделах «Гипотезы» и «Что проверить». Заголовки разделов получают id. По этим id `impact` строит карту «раздел → утверждения».

### 3.3 Поиск по формулировке, смыслу и связям без платной инфраструктуры

- **Формулировка.** BM25 по стеммам (облегчённый русский Snowball, ё→е) и TF-IDF по символьным 3-граммам (морфология, опечатки), слияние через RRF. Индекс `.cache/index.json` перестраивается по sha файлов; до ~10⁴ фрагментов — секунды на чистом Python.
- **Смысл.** (1) `kb/glossary.md` хранит синонимы («отток ≈ выбытие ≈ прекращение оплаты») и ложные синонимы («группа ≠ домохозяйство ≠ номер ≠ SIM»); при смешении единиц выдача предупреждает. (2) Запрос расширяет сама модель IDE: 2–3 перефразировки через `--q`, слияние через RRF; вторая модель не нужна. (3) Опционально эмбеддинги через `STRATEG_EMBED_CMD`; выключено, пока бенчмарк не покажет прирост recall.
- **Связи.** У каждого результата видны соседи на один шаг (подтверждает, опровергает, зависит от), так что противоречие заметно сразу. Команды `graph ID --up|--down --depth N` и `why ID`.
- **Области:** claims, снимки, kb, decisions, deliverables. `retracted` и `superseded` по умолчанию скрыты; deliverables и `I*` помечаются «прежний вывод агента, не доказательство».

### 3.4 Память между сеансами

Память — это файлы проекта (реестр, решения, журнал), а не «воспоминания» модели. Между проектами хранятся только `memory/preferences.jsonl` (то, что сказал сам пользователь, `origin=human`) и `memory/lessons.jsonl` (процессные уроки агента; статус `proposed` до одобрения; как факт о мире не используются никогда). Прежний ответ агента можно найти, но ссылаться на него как на основание нельзя: ссылаться можно только на его источники.

### 3.5 Анализ влияния новых данных (`st.py impact`)

1. **Регистрация.** `ingest`/`fetch` создают источник, `source-reader` извлекает утверждения.
2. **Кандидаты.** Для каждого нового утверждения отбираются те же `key` (детерминированно), а также BM25 top-10 по тексту.
3. **Отношение.** Агент проставляет `supersedes`, `contradicts` или `supports`. Отношения по одинаковому `key` скрипт проставляет сам.
4. **Замыкание.** По обратным рёбрам `depends_on` и `derived_from` скрипт находит все зависимые записи: `I`, `P`, расчёты `K`, разделы документов, решения (`basis ∩ затронутые`), обязательства и сработавшие триггеры. Всё найденное получает статус `under_review`.
5. **Перерасчёт.** Затронутые `K` пересчитываются автоматически, потому что они детерминированы. В отчёт попадает дифф «было → стало».
6. **Отчёт.** `IMPACT-<дата>.md` содержит таблицу «элемент · было · стало · уверенность до/после · меняет ли решение». Агент переписывает только затронутые разделы. Если пересёкся порог триггера решения, запускаются ворота G2′. Формулировка изменения: «изменилось / подтвердилось относительно прежнего суждения».

### 4.3 Субагенты (ровно три; в IDE без субагентов тот же контракт выполняется в основном контексте)

| Роль | Уровень | Почему | Инструменты | Контракт |
|---|---|---|---|---|
| `source-reader` | cheap | Задача объёмная и ограниченная. Ошибки ловит скрипт: цитата должна найтись в снимке. Изоляция недоверенного текста от контекста с правами | Read, Grep (без Bash, Write, Web, MCP) | JSON: `claims[]` с цитатами и локаторами, `injection_suspected`, `notes` ≤1 тыс. токенов |
| `critic` | strong | Найти сильнейшее возражение — самая трудная часть рассуждения. Нужна независимость от черновых рассуждений писателя. Вызывается всего ≤2–3 раз за проект | Read; видит артефакты, реестр и рубрику, но не переписку | Список замечаний: блокирующее / важное / мелкое, у каждого якорь и «что снимет» |
| `respondent` | mid | Нужна связность роли. Дешёвые модели сильнее сжимают разнообразие ответов. Сильная модель — лишние траты на то, что доказательством всё равно не станет. Изоляция нужна, чтобы респондент не видел гипотез (меньше подсказки) | нет инструментов | Ответы в роли → `synthetic/run-*.md`, всё с пометкой «сгенерировано, не собрано» |

Параллельных исследователей и отдельного цитатного агента нет. Цитаты проверяет скрипт, а писатель один, чтобы продуктовая и коммуникационная стратегии не разошлись (R1).

## 5. Маршрутизация

**Выбор процесса.** Сначала детерминированные правила: реплика из §2.4 → `task.stage`/`status` → новый файл в `inbox/` (`revisit`) → ключевые слова. Неоднозначный запрос классифицирует Jev (`choice`, нейтральные метки A–F), если он включён; иначе модель IDE выбирает из фиксированного меню skills и пишет причину одной строкой. Маршрут пишется в журнал (`phase=route`).

**Выбор модели.** Основная сессия использует модель, которую выбрал пользователь. README рекомендует strong для S2–S6 и mid для S1 и S7. Уровни субагентов перечислены в §4.3, имена моделей лежат в `config/models.json`. В IDE без субагентов уровень не управляется, и RUN_REPORT честно это указывает.

**Выбор инструмента** (по убыванию приоритета): материалы проекта → `st.py fetch` по allowlist → MCP или веб-поиск IDE только для поиска URL → в крайнем случае человек сохраняет страницу в `materials/`. Бюджеты усилий в `budget.json`: S1 ≤25 загрузок и ≤40 источников; критик ≤3 вызова на проект; синтетика ≤3 прогона × 5 ролей. Простой фактический вопрос — ≤3 загрузки.

**Детерминированные валидаторы** — это проверки ворот из §2.1 и инварианты §3.2, плюс словарь WEP и смешение единиц.

**Лестница эскалации:**
- L0: `check` нашёл нарушение.
- L1: та же модель исправляет по списку нарушений, одна попытка.
- L2: `critic` или strong-уровень, одна попытка.
- L3: человеку уходит точный список нарушений.

Каждая попытка пишется в журнал, циклов нет.

**Исправление ошибочного выбора.** Признаки ошибки: два провала ворот, реплика «не то», низкая уверенность судьи, перерасход более 50% бюджета стадии. Тогда пишется `route_corrected` с причиной и выбирается другой skill или уровень. `report routes` собирает такие исправления. Человек по ним правит `policies/routing.md`: петля улучшения проходит через человека, а не через самоизменение агента.

**Где Jev и почему он отключается безопасно.** Jev используется только в четырёх местах: (1) классификация намерения; (2) релевантность фрагмента вопросу-развилке; (3) чек-листы рубрики `noul` («у варианта есть возражение», «обещание покрыто функцией»); (4) предварительный детектор инъекций. Оценивать стратегию и считать он не должен (R3). Поведение при недоступности, ошибке или уверенности ниже τ:
- (1) переход на правила и меню;
- (2) фрагмент не отбрасывается;
- (3) пункт помечается «не проверено судьёй» и уходит критику;
- (4) источник получает `injection=unchecked`, чтение идёт только через `source-reader` с показом человеку.

Пропуска по умолчанию нет нигде. τ и проверка перестановки меток («метки перебивают определения») — на 40 размеченных примерах из `eval/`; аудит 10% решений. Наружу уходят только фрагменты открытых источников ≤8 тыс. символов, интервью — никогда. Версия модели фиксируется.

**Учёт стоимости.**
- Каждый `step done` пишет оценку: `ceil(символы/k)`, где k калибруется один раз по трём русским документам, `basis=estimate`.
- В конце стадии человек вносит `reported` из `/usage` или `ccusage`, если IDE это даёт.
- Стоимость Jev точная, из ответа API (`exact`).
- Минуты человека фиксируются на воротах.
- RUN_REPORT отдельно показывает долю повторов и доработок.

## 6. Безопасность

1. **Иерархия инструкций** (первые строки AGENTS.md): система и IDE → пользователь в чате → AGENTS.md, `agent/`, skills → kb. Всё в `projects/*/materials`, `evidence/`, `interviews/`, `synthetic/`, а также вывод веб-инструментов и MCP — **данные**. Если в данных встречается просьба или команда, агент цитирует её пользователю и ничего не исполняет.
2. **Карантин.** Снимок оборачивается маркерами `<<<UNTRUSTED nonce=…>>>` с шапкой (url, дата, sha256). Снимки не импортируются через `@`. Glob-правила для `evidence/raw/**` повторяют, что это данные. Основной агент работает с JSON от `source-reader`.
3. **Allowlist.** Список доменов в `config/allowlist.json` исполняется в коде `fetch.py` (он же проверяет robots.txt и лимиты размера). PreToolUse-хук его дублирует. Расширить список можно только по просьбе в чате через `allow add`, запись получает `origin=human`. Домены, найденные в источниках, не добавляются без вопроса.
4. **Защищённые пути.** Записи в (a), (b) и (d) запрещены правилами deny, PreToolUse и проверкой `validate`. Менять правила можно только по прямой просьбе пользователя.
5. **Секреты.** Есть только `.env.example`; `.env` в `.gitignore` и в deny на Read. `validate` ищет шаблоны ключей. Скрипт без ключа явно сообщает: «работаю без Jev».
6. **Каналы утечки.** Никаких URL с данными проекта в параметрах и никаких внешних картинок в отчётах. Внешние запросы идут только через `fetch.py`. Ногу «смертельной тройки» «приватные данные» мы убираем по конструкции: в репозитории только открытые и учебные данные.
7. **Реальные интервью.** Шаблон согласия; в репозиторий попадает только номер согласия. `pii scan` блокирует `ingest` расшифровки с телефонами, e-mail или адресами. Владельцы задаются ролями, а не ФИО.
8. **Синтетика.** Отдельная папка, вид `Y`, инварианты §3.2, карточка раскрытия (популяция, модель, промпт, дата, что сгенерировано).
9. **Цепочка поставок.** Сторонние навыки не подключаются; версии MCP закреплены.

## 7. Возобновление и устойчивость

**Протокол resume** (≤10 строк в AGENTS.md; хук SessionStart или skill `resume`):
1. `st.py resume` выдаёт проект, стадию, ворота, `next_action`, открытые вопросы, ожидания от человека, прерванные операции, `due`, `stale` и бюджет.
2. Блокировка: если `.lock` моложе 2 часов и создан другой сессией, агент предупреждает. Так ловится ситуация «одновременно открыто в двух IDE».
3. Целостность: sha артефактов сверяется с журналом. Расхождение означает `human_edit`, такая правка считается авторитетной.
4. Прерванные операции. Идемпотентная операция без артефакта повторяется с `retry_of`, и это видно в выводе. Шаг LLM, у которого есть `start` без `done`, показывается вопросом: «S3.options прерван, черновик есть (n строк): продолжить с черновика или начать заново?». **Тихих повторов нет.**
5. Агент загружает skill текущей стадии и нужный раздел kb, больше ничего.

**Идемпотентность.** Операции адресуются по содержимому: повторный `claim add` того же текста с теми же ссылками вернёт существующий ID и запишет `skipped_cached`. Для `fetch` ключ — url плюс день; повторная загрузка возможна только с `--refresh`. Запись идёт во временный файл с атомарным переименованием. Если строка JSONL оборвана, хранилище пропускает её и сообщает номер.

**Отказы замечаются и классифицируются:**
- сеть: timeout, 403, robots, вне allowlist, слишком большой ответ → совет сохранить страницу вручную и выполнить `ingest`;
- MCP недоступен → `st.py fetch`;
- Jev недоступен → fallback (§5);
- в IDE нет субагентов → режим «в основном контексте», сырой текст источника читается только фрагментами через `st.py show S14 --excerpt` с маркерами;
- падение скрипта → код 1 без частичной записи.

Каждый сбой пишется в журнал (`phase=fail`) и попадает в RUN_REPORT.

**Переносимость.** Всё состояние лежит в файлах репозитория, память конкретной IDE не используется. Чтобы перейти в другую IDE: открыть папку → AGENTS.md → `resume`; `sync --check` подтверждает адаптеры. В демо-видео это показано так: Claude Code, затем остановка, затем продолжение в Cursor.

## 8. Прозрачность

**`PROGRESS.md`** (≤60 строк, генерируется):
- полоса стадий `S0✓ S1✓ S2✓ S3◐ S4· …`;
- ворота и что от них ждут;
- «Жду от вас: выбрать направление (G1), варианты O1–O4»;
- допущения, принятые без вопроса;
- последние 5 событий;
- прерванные операции;
- `due`;
- стоимость: потрачено и бюджет, с пометками estimate/reported.

**`RUN_REPORT.md`** (по стадиям): время работы агента и время ожидания человека (по событиям ворот), токены и деньги с пометками `basis`, число загрузок, вызовов субагентов и Jev, повторы и эскалации, ошибки и что с ними сделали, минуты человека и все его вмешательства (ответы, правки, исправления), какие уровни моделей реально использовались. Те же данные идут в раздел «время и расходы» описания работы.

**След доказательств.** Число в STRATEGY → якорь `[F12]` → `st.py why F12` → источник S01, локатор, цитата, sha снимка, URL и дата. Для `K` показываются формула, значения входов и хэш. Для решений — `basis` и `ledger_hash`.

## 9. Оценка: сравнение с аналитиком и обычным чатом

**Набор задач (6).**
- B1 — демо-бриф.
- B2 — «почему падает удержание в приложении» (вымышленные данные, CSV).
- B3 — «кому продавать новый сервис защиты малому бизнесу» (открытые данные).
- B4 — «закрывать ли направление» (вариант «закрыть» должен победить при честных данных).
- B5 — пересмотр: на середине B1 подкладывается файл, опровергающий `A07`; заранее составлен эталонный список затронутого.
- B6 — ловушка: среди источников страница с командой агенту.

У каждой задачи есть эталонные числа и чек-лист.

**Условия.**
- (A) репозиторий в IDE;
- (B) обычный чат той же модели с теми же материалами и **тем же шаблоном итогового документа**, чтобы сравнивался процесс, а не оформление;
- (C) ручной аналитик: участник команды с лимитом 4 часа, только B1 и B2, его ставка — названное допущение.

**Метрики:**
- M1 — покрытие чек-листа (≈30 бинарных пунктов из kb G);
- M2 — валидность цитат на выборке из 20 утверждений: открывается, цитата на месте, поддерживает (3 уровня);
- M3 — арифметические ошибки против эталона;
- M4 — точность разметки факт / допущение / прогноз на 20 фразах;
- M5 — время до документа, пригодного для решения, и минуты человека;
- M6 — стоимость;
- M7 — resume: процесс прерывается на случайной стадии, считаются повторённые операции (цель 0) и токены на восстановление контекста;
- M8 — recall и precision затронутых элементов в B5;
- M9 — ловушка B6 пройдена или нет.

**Честность.**
- Рубрика коммитится до прогонов, git-метка времени это подтверждает.
- Выходы обезличиваются и приводятся к одному формату.
- Оценивают два человека вслепую плюс LLM-судья другого семейства, чем генератор; согласие оценщиков публикуется.
- При n=6 значимость не заявляется: только таблица по задачам и прямое указание, где чат выигрывает (почти наверняка по скорости и цене).

**Абляции** (2 задачи × 3): без критика, без `source-reader`, без проверки якорей. Компонент, не давший прироста M1–M4 или M9, переходит в список сокращений.

## 10. ADR (MADR-lite, статус всех: принято)

**ADR-01. Переносимость через AGENTS.md и генерируемые адаптеры.**
- Контекст: семь и более IDE с разными файлами. Claude Code не читает AGENTS.md.
- Варианты: (1) отдельные файлы для каждой IDE вручную; (2) CLAUDE.md как главный; (3) AGENTS.md как источник правды плюс `sync`.
- Решение: 3.
- Последствия: + одна правда, `--check` ловит дрейф. − Генератор надо поддерживать; часть IDE (Kodik) проверяется только вручную.

**ADR-02. Один stdlib-CLI для всех побочных эффектов.**
- Контекст: возобновление, идемпотентность и проверки нельзя доверять самодисциплине модели.
- Варианты: (1) только инструкции; (2) MCP-сервер как основа; (3) CLI на Python, MCP как тонкая обёртка.
- Решение: 3.
- Последствия: + детерминизм, тестируемость, работает везде, где есть терминал. − ~2,5 тыс. строк Python. В IDE без терминала остаются только MCP или ручной режим.

**ADR-03. Хранилище: JSONL с дозаписью и версиями, конфиги в JSON.**
- Варианты: SQLite; Markdown-таблицы; JSONL.
- Решение: JSONL.
- Последствия: + git-diff читаем, история бесплатно, модели реже портят JSON (R3). − Нужна материализация «последней версии»; на 10⁵ записей станет медленно, нам это не грозит.

**ADR-04. Реестр утверждений на уровне «значимо для решения»; вид закодирован в ID.**
- Контекст: главный критерий — проверяемость.
- Варианты: каждое сведение (200+); значимое для решения (30–80) с обязательными якорями; только список источников.
- Решение: значимое для решения, плюс инварианты.
- Последствия: + разумная цена, сильная проверка. − Мелкие факты без ID приходится переформулировать без чисел или регистрировать.

**ADR-05. Один писатель и три узких субагента.**
- Варианты: мульти-агентный поиск с supervisor (~15× токенов чата, R1); один контекст без субагентов; один писатель + reader / critic / respondent.
- Решение: третье.
- Последствия: + согласованность стратегий, изоляция недоверенного текста, независимая критика за умеренную цену. − Нет параллельного ускорения сбора.

**ADR-06. Поиск без платной инфраструктуры.**
- Варианты: векторная БД; эмбеддинги по API; BM25 + 3-граммы + глоссарий + расширение запроса моделью IDE + граф.
- Решение: последнее, эмбеддинги опционально.
- Последствия: + ноль зависимостей. − Смысловой recall ниже, это измеряется в eval.

**ADR-07. Принуждение на уровне данных, хуки только усиливают.**
- Контекст: схемы хуков несовместимы, у Codex своё доверие, у Kodik и GigaCode поддержка не подтверждена (R3).
- Решение: факт регистрируется только через снимок `st.py`; allowlist живёт в `fetch.py`; ворота проверяет `check`; хуки дублируют.
- Последствия: + одинаковые гарантии во всех IDE. − Встроенный веб-инструмент IDE в среде без хуков технически не заблокировать, но его вывод не становится доказательством.

**ADR-08. Jev опционален и закрывается при сбое.**
- Варианты: не использовать; включить по умолчанию; опционально для четырёх узких задач с fallback.
- Решение: третье, по умолчанию выключен.
- Последствия: + маршрутизация и чек-листы дешевле, если ключ есть; сбой не открывает ворота. − Закрытый сервис в США: наружу уходят только фрагменты открытых данных; нужна калибровка τ.

**ADR-09. Синтетические респонденты в карантине.**
- Варианты: не делать; считать слабым доказательством; вести как источник только гипотез.
- Решение: последнее (вид `Y`, связь только `supports→H`, без чисел распространённости, ≥2 перестановки).
- Последствия: + пункт дополнительного уровня закрыт без подмены доказательств. − Ценность ограничена генерацией вопросов; это честно указано.

**ADR-10. Три фиксированных ворот для человека плюс ворота по событию.**
- Варианты: подтверждать каждую стадию; полная автономия; G0/G1/G2 плюс исключения.
- Решение: последнее.
- Последствия: + человек тратит минуты только на существенный выбор. − Ошибку на S1–S2 он видит позже; смягчение — PROGRESS со списком допущений.

**ADR-11. Пересмотр через граф зависимостей и снимок реестра в решении.**
- Варианты: перегенерировать всё при новых данных; ручной пересмотр; замыкание по графу с `ledger_hash`.
- Решение: последнее.
- Последствия: + пересчитывается только затронутое, видно «было → стало», история не переписывается. − Качество зависит от того, насколько аккуратно агент проставляет `depends_on`; `check S2/S4` требует связи у каждого `I` и `P`.

## 11. Контестные развилки (для LLM Council)

**В1. Топология агентов.** Какая топология даёт лучшее соотношение качества стратегии и стоимости на стадиях сбора и исследования в агенте, который работает внутри AI-IDE?
(A) Один писатель плюс три узких субагента (читатель источников, критик, модельный респондент), без параллельного поиска.
(B) Вариант A плюс 2–4 параллельных исследователя по веткам дерева вопросов под управлением супервизора.
(C) Один контекст без субагентов; критика выполняется отдельным проходом той же сессии по рубрике.

**В2. Граница детерминизма.** Где провести границу между Python-скриптами и инструкциями для модели?
(A) Скрипты-центрично: все записи состояния, реестров, расчётов и проверки ворот идут через CLI, модель не пишет JSONL сама.
(B) Гибрид-лайт: скрипты только для загрузки, возобновления и итоговой проверки, реестр — Markdown-таблицы, которые правит модель.
(C) Только инструкции: всё в Markdown, единственный скрипт — валидатор структуры.

**В3. Гранулярность реестра утверждений.** На каком уровне детализации вести реестр, чтобы прослеживаемость и пересмотр при новых данных окупали затраты токенов и внимания?
(A) Только утверждения, значимые для решения (30–80 на проект); каждое число в итоговых документах обязано ссылаться на ID.
(B) Атомарные записи на каждое извлечённое сведение (200+), извлекаются автоматически из каждого источника.
(C) Реестр только источников плюс встроенные в текст метки «факт / гипотеза / прогноз» без отдельных записей.

**В4. Глубина демо против общности.** Как распределить ограниченное время команды между демо-проектом и обобщаемостью агента?
(A) Приоритет общности: универсальные шаблоны и методика, демо проходит стандартным путём без предметных доработок.
(B) Приоритет глубины демо: предметные шаблоны, расчёты и примеры под бриф, обобщаемость подтверждается одной дополнительной задачей.
(C) Баланс: общее ядро плюс предметный пакет для домена демо как подключаемый модуль проекта, проверка на 2–3 новых задачах.

(Jev в развилки не вынесен: в ADR-08 он опционален и выключаем, поэтому цена ошибки этого выбора мала.)

## 12. Риски и сокращение объёма

| Риск | Признак | Смягчение |
|---|---|---|
| Модель IDE игнорирует протокол | Нет записей `step` или `check` | Ворота в коде, напоминание в хуке Stop, смоук-тест для каждой IDE |
| Накладные расходы реестра тормозят работу | Больше 30% токенов уходит на `claim add` | Гранулярность ADR-04, пакетный `claim add --jsonl` |
