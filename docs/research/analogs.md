# Аналоги и заимствуемые паттерны для агента «Стратег Фабрики продуктов»

Дата исследования: 2026-11-22. Страницы прочитаны через WebFetch, содержимое пересказано. Метки надёжности: **[вендор]** – заявления самого продавца или конкурента, **[независимо]** – обзор, исследование или рецензируемая работа, **[наш вывод]** – наша оценка, а не факт из источника. Не удалось получить содержательных данных по Aha! и по деталям Cloverpop (только вендорский анонс 2018 г.), поэтому паттернов оттуда не берём.

## 1. Open-source наборы PM-навыков для Claude Code / Cursor / Codex

**phuryn/pm-skills** – https://github.com/phuryn/pm-skills
- Что это: маркетплейс из 9 плагинов, около 68 навыков и 42 команды. Навык – `skills/*/SKILL.md`, подгружается автоматически. Команда – `/discover`, `/strategy`, `/plan-launch`, она сцепляет навыки в процесс. Пример: `/discover` = идеи, затем допущения, затем приоритизация допущений, затем эксперименты. После команды предлагаются следующие шаги.
- Заимствуем: разделение «знание (skill) / процесс (command)» и подсказку следующего шага после каждого этапа.
- Подводные камни: команды работают только в Claude, в Codex и Cursor остаются одни навыки. Установка выборочных навыков ломает связки между ними. Внутри README расходятся счётчики (68 и 69). [наш вывод] Это библиотека фреймворков, проверки источников и учёта допущений в описании нет.

**deanpeters/Product-Manager-Skills** – https://github.com/deanpeters/Product-Manager-Skills
- Что это: около 77 навыков трёх типов: workflow (многодневные процессы), interactive (3–5 вопросов, затем нумерованные рекомендации), component (шаблоны). В корне лежат `AGENTS.md`, `CLAUDE.md`, `START_HERE.md`, есть `scripts/` и валидатор: навык без раздела Input не проходит. Намеренно нет `$ARGUMENTS`, чтобы навыки работали в любой среде.
- Самый ценный навык – `autonomous-investigation` (https://raw.githubusercontent.com/deanpeters/Product-Manager-Skills/main/skills/autonomous-investigation/SKILL.md): лимит уточняющих вопросов (обычно 3), затем работа на помеченных допущениях; короткий план-чекпойнт до поиска; метки Fact (ссылка, которую можно проверить) / Inference / Assumption; пробелы в отдельном списке, а не четвёртой меткой; перечень того, что запрещено выдумывать (цены, доли рынка, клиенты); фиксированная схема вывода для сравнения прогонов; в конце ровно четыре варианта продолжения.
- Подводные камни: workflow задуман как рекомендуемый маршрут, а не как пайплайн с обязательными шагами. Лицензия CC BY-NC-SA, копировать текст нельзя, заимствуем только идеи. Счётчики навыков расходятся (70 и 77).

**product-on-purpose/pm-skills** – https://github.com/product-on-purpose/pm-skills
- Что это: Apache 2.0, 68 навыков по модели Triple Diamond. У каждого навыка три файла: `SKILL.md` (метод), `TEMPLATE.md`, `EXAMPLE.md`. Есть 10 `/workflow-*` команд, `/chain`, пять субагентов (в том числе `pm-critic` для состязательной проверки артефактов и аудитор каталога), валидатор навыков, 200+ образцов выходных документов. Автообнаружение через `AGENTS.md` в Claude Code, Copilot, Cursor, Windsurf, Codex, OpenCode.
- Заимствуем: тройку «метод + шаблон + эталонный пример», критика как отдельного субагента, валидатор структуры, образцы выходов как тесты качества.
- Подводные камни: субагенты нативны только для Claude Code, MCP-спутник заморожен, CLI по умолчанию шлёт телеметрию (отключаем и не берём такие компоненты).

**anthropics/knowledge-work-plugins** (плагин product-management) – https://github.com/anthropics/knowledge-work-plugins
- Что это: папка плагина = `.claude-plugin/plugin.json` + `.mcp.json` (коннекторы Jira, Linear, Notion, Amplitude, Intercom и др.) + `commands/` + `skills/`. Только markdown и JSON, без сборки.
- Заимствуем: идею «чистые файлы, правятся без кода». Подводный камень: это общий стартовый шаблон, под компанию его надо дорабатывать.

**BMAD-METHOD** – https://github.com/bmad-code-org/BMAD-METHOD
- Что это: agile-метод для разработки ПО. Из PM-части интересны: Product Brief Coach с журналом решений, PRFAQ Coach (метод «от конца»), Forge Idea (проверка сырой идеи вопросами от разных ролей), Advanced Elicitation (структурный второй проход по тексту ИИ), `correct-course` (анализ изменения по PRD, эпикам, архитектуре, UX с выдачей предложения об изменении), список отложенных находок.
- Заимствуем: второй проход-критик и разбор влияния изменения на уже созданные документы. Подводный камень: [наш вывод] метод заточен под поставку софта и тяжеловесен для одной стратегической задачи.

**Риск цепочки поставок навыков** – https://snyk.io/articles/7-claude-skills-product-managers/ [независимо, но Snyk продаёт security]
- Snyk приводит данные: в 36% проверенных навыков найдена prompt injection, из 3984 просканированных навыков 13,4% имеют критическую проблему. Публикация навыка требует одного `SKILL.md`, подписи и проверки нет. Совет: читать SKILL.md и скрипты, смотреть `allowed-tools`.
- Вывод для нас: сторонние навыки не подключаем, свои пишем сами.

## 2. Коммерческие AI-инструменты для продуктологов

- **ChatPRD** – https://www.chatprd.ai , обзор https://makerstack.co/reviews/chatprd-review/ . Работы: черновик PRD, one-pager, истории из заметок; ревью чернового PRD (слабая постановка проблемы, нет метрик успеха); контекст продукта в проектах; экспорт в Notion, Slack, Linear. Хвалят: меньше переписывать, чем после обычного чата, и «коуч»-обратная связь. Ругают: не управляет роадмапом и задачами, конкурирует с ChatGPT/Claude по цене ($15/мес), без реальных данных о клиентах черновик получается шаблонным.
- **Productboard AI** – разбор https://dev.to/pickuma/productboards-ai-features-reviewed-do-they-actually-help-you-prioritize-31e3 [независимо]. Работы: раскладка фидбэка по фичам, сводки, Pulse (растущие и падающие темы). Хвалят: сортировку потока заметок. Ругают: сводка стирает силу сигнала (пожелание и угроза ухода выглядят одинаково), без данных CRM ИИ не видит денег и риска оттока, тренды на малой выборке есть шум, приоритизация остаётся обычным взвешенным скорингом.
- **Dovetail** – отзывы https://www.capterra.com/p/174077/Dovetail//reviews/ . Единое хранилище интервью, тикетов, отзывов; сводки и автотеги. Хвалят: экономию времени, поиск по хранилищу. Ругают: часть пользователей считает ИИ неточным, тяжёлая настройка таксономии тегов, инсайты трудно находить, рост цен при смене тарифов. Маркетинг «ask, never guess» не раскрывает механизма цитирования (https://www.dovetail.com/blog/customer-intelligence-purpose-built-ai-vs-general-llms) [вендор].
- **BuildBetter** – https://blog.buildbetter.ai/best-ai-tools-for-writing-prds-grounded-in-customer-evidence/ [вендор, рейтинг в свою пользу]. Идея «доказательного PRD»: каждое требование ссылается на цитату или таймкод разговора. Критика PRD-генераторов без опоры на данные: они правдоподобно выдумывают потребности. Берём принцип, цифры из статьи не берём.
- **Kraftful, Zeda.io** – https://www.producthunt.com/p/kraftful/kraftful-4-0 , https://www.producthunt.com/products/zeda-io/reviews . Анализ тикетов и звонков, AI-интервью, черновики PRD. Отзывы малочисленные, независимых данных о качестве нет, ссылки на первоисточник не описаны.
- Общий вывод [наш вывод]: инструменты хорошо закрывают одну работу (черновик документа или разбор фидбэка), но ни один не ведёт путь «размытый запрос, проверка, варианты с возражениями, рекомендация, план проверки, пересмотр».

## 3. Deep-research агенты

**Anthropic multi-agent research system** – https://www.anthropic.com/engineering/multi-agent-research-system
- Паттерны: руководитель сохраняет план во внешней памяти и запускает субагентов с отдельными контекстами; отдельный CitationAgent привязывает утверждения к источникам после черновика. Правила масштабирования усилий записаны в промпт: простой факт – один агент, 3–10 вызовов; сравнение – 2–4 субагента; сложное – 10+. Задание субагенту содержит цель, формат вывода, источники и инструменты, границы. Оценка: около 20 реальных запросов, LLM-судья по точности фактов, точности цитат, полноте, качеству источников, эффективности инструментов, плюс человек. Сбои: возобновление с точки отказа, чекпойнты.
- Цена: агент тратит около 4x токенов чата, мультиагент около 15x; расход токенов объясняет около 80% разброса качества. Значит, эта архитектура оправдана только для задач высокой ценности.

**LangChain Open Deep Research** – https://www.langchain.com/blog/open-deep-research , репозиторий https://github.com/langchain-ai/open_deep_research (архивирован)
- Паттерн scope, research, write: уточняющие вопросы, затем краткий **research brief** как опорный документ, затем supervisor и субагенты в изолированных контекстах, затем одно финальное написание. Параллельная запись разделов давала несвязный текст, поэтому писатель один.
- Роли модели (суммаризация, поиск, сжатие, отчёт) настраиваются по отдельности. Прогон бенчмарка стоил около $46 на конфигурации по умолчанию и около $187 на более дорогой.

**GPT Researcher** – https://github.com/assafelovic/gpt-researcher
- Планировщик делит задачу на вопросы, исполнители собирают материал, каждый источник суммируется и привязывается к ссылке, затем публикатор собирает отчёт. Режим Deep Research идёт деревом с заданными глубиной и шириной: около 5 минут и $0,40 за прогон (по их данным). Есть MCP-ретривер и фильтр контекста, в том числе Jev.
- Подводный камень: опора на повторяемость факта в разных источниках – эвристика частоты, а не проверка. Показатели с собственного бенчмарка из 28 задач [вендор].

**STORM / Co-STORM** – https://github.com/stanford-oval/storm
- До написания идёт «предписьменный» этап: разные точки зрения из похожих материалов управляют вопросами, имитируется диалог автора с экспертом, отвечающим по найденным источникам, затем строится иерархический план. Авторы прямо пишут, что результат требует редактуры.
- Заимствуем: перспективы для поиска гипотез и план перед текстом.

**ChatGPT / Gemini / Perplexity**
- OpenAI (https://developers.openai.com/api/docs/guides/deep-research): фоновый режим для долгих прогонов, цитаты с URL и местом в тексте, отдельный список всех просмотренных источников (их больше, чем процитированных); публичный поиск и закрытые MCP-запросы советуют разделять из-за prompt injection.
- Обзор Sarah Constantin (https://sarahconstantin.substack.com/p/ai-deep-research-tools-reviewed) [независимо]: выдуманных утверждений не нашла, но источники и привязка утверждений различаются; потолок около 40 источников. Perplexity в тестах цитировал малую часть просмотренного и давал разные ссылки при повторе (https://c3.unu.edu/blog/deep-research-revolutionizing-information-synthesis-with-ai).

**Проверка цитат** [независимо, препринты]
- DeepTRACE (https://arxiv.org/abs/2509.04499v1): точность цитат у систем от 40% до 80%, много утверждений не подтверждены собственными источниками, на спорных темах ответы односторонние.
- Работа о «галлюцинированных ссылках» (https://arxiv.org/pdf/2604.03173): 3–13% процитированных URL выдуманы, 5–18% не открываются; deep-research агенты цитируют больше и ошибаются чаще. Инструмент urlhealth (проверка ответа и Wayback Machine) в цикле самоисправления снизил число нерабочих ссылок до менее 1%.

**Jev (специализированный судья)** – https://spring.io/blog/2026/10/02/spring-ai-modular-rag-typesafe-jev , https://hindsight.vectorize.io/blog/2026/09/24/adding-jev-reranker-what-we-learned
- Jev принимает запрос и отрывок и возвращает числовую оценку. Фильтр задаёт четыре узких вопроса: есть ли prompt injection, противоречит ли посылке, релевантно ли, содержит ли доказательство. Нужен API-ключ TypeSafe, текст уходит на внешний сервис.
- Уроки: один вопрос с выбором из всего пула дешевле и точнее попарных оценок (0,94 против 0,87 recall@1 при примерно 1/30 вызовов); вариант «ничего не подходит» ломал выдачу; жёсткая обрезка теряла около 19% нужных доказательств; при недоступности API компонент Spring по умолчанию пропускает всё без проверки, что для безопасности плохо. [вендор/практики] Для нас это пример роутера-классификатора, но обязателен запасной путь без внешнего ключа.

## 4. Синтетические пользователи и ИИ-респонденты

- **NN/g** – https://www.nngroup.com/articles/synthetic-users-vs-human-respondents/ [независимо]. Тест: 120 синтетических против 604 реальных ответов на один открытый вопрос. Главный вывод совпал, но синтетика сжалась в примерно дюжину формулировок против 50+ у людей (mode collapse), различия между ролями сглажены (93% синтетических PM против 44% реальных использовали термин «UX»), платформа сама переформулировала вопрос. Вердикт: не считать доказательством, годится для гипотез.
- **Обзор MeasuringU** – https://measuringu.com/review-of-experiments-with-synthetic-users/ : из 12 работ 9 обнадёживающих находок и 14 тревожных; в 14 классических психологических исследований воспроизвелись 3; дисперсия занижена, эффекты преувеличены; в UX-интервью не хватает глубины. Совет: только направляющий сигнал; платформам верить только после проверки на реальных данных.
- **Бенчмарк 2607.26348** – https://arxiv.org/pdf/2607.26348 : модель не лучше простой таблицы по демографии на уровне отдельного респондента; демография переоценивается как предиктор (стереотипизация); различия между сегментами завышены в 2–4 раза, неверный целевой сегмент выбирался примерно в половине случаев для США; перестановка вариантов ответа меняла 10–23% предсказаний; крупные модели не лучше. Совпадение средних по совокупности вводит в заблуждение.
- **Персоны, написанные LLM** – https://arxiv.org/html/2503.16527 : смещаются к «прогрессивному» и позитивному, избегают трудностей.
- **Чеклист раскрытия** – https://arxiv.org/pdf/2512.00461 : указывать целевую популяцию, происхождение данных, какие атрибуты сгенерированы LLM, отдельно экологическую валидность.
- **Опрос User Interviews (n=150, май 2026)** – https://www.userinterviews.com/state-of-synthetic-users-report [вендор исследований]: главные опасения – точность (88%), чрезмерное доверие заказчиков (79%), смещение против меньшинств (79%); у 63% организаций нет политики.
- **Вендоры.** Synthetic Users (https://www.syntheticusers.com/): «паритет» 85–92% с людьми по собственным исследованиям (мера – тематическое пересечение), показатель насыщения, привязка к своим транскриптам; в FAQ называет себя «ко-пилотом», в заголовках обещает больше. Evidenza (описание конкурента https://neuroflash.com/blog/digital-twin-comparison/neuroflash-vs-evidenza/): точность 88%, методика не раскрыта, независимого аудита нет. Заявления не проверены.
- **Как маркировать:** единого стандарта нет (в опросе 76% говорят «synthetic users»). Берём практику: явная пометка «сгенерировано, не собрано», описание метода и модели, область применения, запрет клеймить как распространённость.

## 5. Журналы решений и отслеживание

- **MADR** – https://adr.github.io/madr : YAML-шапка (статус, дата, кто решает, кого консультировали, кого информировали), контекст и проблема, драйверы решения, рассмотренные варианты, итог с обоснованием, последствия (в v3 плюсы и минусы объединены), **Confirmation** (как проверить, что решение выполнено), плюсы и минусы вариантов, ссылки; в «Дополнительно» можно записать, когда пересматривать. Пересмотр и допущения опциональны и без структуры.
- **Decision journal (Farnam Street)** – https://fs.blog/decision-journal : ситуация, рамка, варианты и причины отказа, диапазон исходов, ожидаемый исход с вероятностями, состояние автора. Запись делается до исхода, чтобы не переписывать прошлое задним числом. В шаблоне нет даты пересмотра.
- **Cloverpop** – https://www.cloverpop.com/resources/product-update-system-of-record-for-decisions [вендор, 2018]: кто, что, зачем, теги, поиск, график результатов решений, скорость принятия, Slack. О допущениях в анонсе не сказано.
- **Pre-mortem с kill criteria** – https://skills.sh/coowoolf/insighthunt-skills/pre-mortem-kill-criteria : идея усилить pre-mortem заранее принятыми действиями на конкретные негативные сигналы. Полный текст навыка страница не показала.
- **Трассировка памяти агентов** – https://arxiv.org/pdf/2606.04990 [обзор 71 работы]: при записи в память хранить тип источника, время, автора, подтверждающие данные, преобразование, уверенность, историю обновлений; различать происхождение связи (измерена средой, выведена судьёй, заявлена агентом, вычислена); заявленные агентом цитаты считать слабейшим доказательством. Риски: «заражённая» память, слабый вывод, сохранённый как факт, устаревшая запись без отметки замены.

## 6. Реестр доказательств и оценка уверенности

- **ICD 203** – https://archive.dni.gov/files/documents/ICD/ICD-203.pdf : отделять сведения от допущений и суждений; ключевые допущения называть и указывать, как изменится вывод, если они неверны; описывать надёжность источника (полнота, возраст, способ получения, возможное смещение); вероятность выражать терминами из одной строки таблицы (диапазоны от 1–5% до 95–99%); уверенность в суждении (качество и объём доказательств) не смешивать с вероятностью в одной фразе; рассматривать конкурирующие гипотезы и показатели, которые изменили бы вывод; отмечать, что суждение изменилось против прежнего.
- **Sherman Kent, Words of Estimative Probability** – https://www.cia.gov/resources/csi/static/Words-of-Estimative-Probability.pdf : в оценке 1951 года фраза «серьёзная возможность» читалась авторами и читателями от 20% до 80%; предложены пять слов с числовыми диапазонами.
- **Admiralty / NATO** – https://en.wikipedia.org/wiki/Admiralty_code : надёжность источника A–F и достоверность сведения 1–6 оцениваются отдельно, код прикрепляется к элементу информации, а не к выводу. [наш вывод] У LLM шесть градаций дают ложную точность, хватит трёх.
- **GRADE** – https://bestpractice.bmj.com/info/evidence/learn-ebm/what-is-grade/ : четыре уровня уверенности; понижают за риск смещения, неточность, несогласованность, непрямоту (другая популяция или показатель), смещение публикаций; повышают редко; общая оценка не выше самого слабого критичного результата. Ценность в прозрачности рассуждения.
- **ACH (Heuer)** – https://en.wikipedia.org/wiki/Analysis_of_competing_hypotheses : матрица «гипотезы x свидетельства», главное – диагностичность (свидетельство, отличающее гипотезы) и опровержение, а не подтверждение; в конце проверка чувствительности и список признаков для наблюдения. Критика: трудоёмко, на больших объёмах громоздко, сам набор гипотез не проверяется, слабые эмпирические доказательства пользы.

## Что заимствуем в наш агент

1. **Реестр утверждений (claims ledger)** как файл в репозитории: id, текст, тип (Fact / Inference / Assumption / Hypothesis / Forecast / SYNTHETIC), источник с локатором (URL или путь, цитата, дата получения), качество источника (3 уровня), прямота (GRADE-lite: тот ли сегмент, период, показатель), уверенность (4 уровня), статус (активно / заменено / отозвано), связи «подтверждает / опровергает». Основа: метки Peters, ICD 203, GRADE, поля трассировки памяти.
2. **Раздел «Известно / Источник / Неизвестно»** строится из реестра; пробелы живут отдельным списком с причиной и способом закрыть, а не метками.
3. **Постановка задачи**: бюджет вопросов (не больше 3–5 за раунд, остальное идёт как помеченные допущения), затем **research brief** – один файл-якорь с вопросом, целью, получателем, ограничениями и решением, которое можно изменить. Показываем краткий план до начала поиска.
4. **Исследование от вопросов, меняющих решение**: перспективы в духе STORM для генерации вопросов; правила масштабирования усилий по сложности и бюджет шагов; субагенту выдаётся контракт: цель, формат, допустимые источники, границы.
5. **Писатель один**: субагенты ищут и критикуют параллельно, финальную стратегию пишет одна сессия, чтобы продуктовая и коммуникационная части не разошлись.
6. **Скрипт проверки ссылок и цитат**: существование (HTTP, Wayback), затем наличие цитаты в сохранённой копии страницы, затем проверка «поддерживает ли отрывок утверждение» отдельным судьёй. Хранить копию и хэш, различать «просмотрено» и «процитировано».
7. **Варианты и возражения**: минимум три, включая «оставить как есть» и «закрыть направление»; отдельный субагент-критик (по образцу `pm-critic`) формулирует сильнейшее возражение; для выбора между объяснениями проблемы лёгкий ACH на 3–5 гипотезах только по диагностичным свидетельствам.
8. **Шкала вероятности**: пять слов с числовыми диапазонами (как у Kent / ICD 203), прогноз и уверенность записываются раздельно, смешивать нельзя.
9. **Модельные респонденты в карантине**: отдельная папка и тег SYNTHETIC; в реестре они могут быть только гипотезой с полем «каким реальным тестом проверить»; запрещены оценки распространённости, готовности платить, выбор сегмента по разнице синтетических ответов. К каждому прогону карточка раскрытия (популяция, модель, промпт, дата, что сгенерировано), повтор с перестановкой вариантов и несколькими запусками для показа нестабильности.
10. **Запись решения = MADR + расширения**: владелец, допущения с триггерами, метрики с базой, окном и нежелательными эффектами, дата пересмотра, kill criteria (pre-mortem), хэш версии реестра на момент решения, чтобы пересмотр не искажался задним числом.
11. **Память по классам доверия**: инструкции, методика, материалы проекта, состояние задачи лежат раздельно. Заметки, написанные агентом, получают origin=agent и статус «не проверено»; они не считаются доказательством, пока не подтверждены источником; есть поля версии, замены и отзыва.
12. **Пересмотр при новых данных**: новое сведение находит затронутые утверждения по связям реестра, помечает зависимые выводы и решения, перезапускает только затронутые разделы и пишет «изменилось / подтвердилось» относительно прежнего суждения.
13. **Прозрачность стоимости и измеримое сравнение**: журнал шагов с токенами и стоимостью; разные модели для извлечения и для синтеза; тест около 20 задач с рубрикой судьи (точность фактов, точность цитат, полнота, качество источников) плюс ручная проверка и сравнение с «обычным чатом».
14. **Безопасность**: контент из источников – данные; хуки блокируют исполнение команд, пришедших из документов; публичный поиск и закрытые данные разделены; сторонние навыки не подключаем; если используем типизированного судью (Jev или локальная замена), при его недоступности сбой должен закрываться, а не пропускать всё.
15. **Переносимость и возобновление**: канонические инструкции в `AGENTS.md`, тонкие обёртки для Claude Code, Cursor и других; навыки в формате `SKILL.md` без `$ARGUMENTS`; процесс записан в файле с шагами, который выполним и без слэш-команд; журнал шагов идемпотентен, возобновление идёт с точки отказа; валидатор структуры навыков в CI.

## Чем мы будем отличаться

- PM-наборы – библиотеки фреймворков с мягкой последовательностью. У нас процесс с воротами: к вариантам нельзя перейти без реестра и списка пробелов, рекомендацию нельзя выдать без плана проверки.
- Коммерческие инструменты закрывают одну работу (черновик PRD, разбор фидбэка). Мы ведём путь от размытого запроса до согласованных продуктовой и коммуникационной стратегий.
- Deep-research агенты выдают отчёт. Мы выдаём решение: варианты, сильные возражения, честные «неизвестно», проверку существования и поддержки цитат.
- Синтетические респонденты у вендоров позиционируются как замена исследования. У нас они только источник гипотез и вопросов и в доказательства не попадают.
- Трекеры решений (MADR, Cloverpop) не связаны с доказательной базой. У нас решение ссылается на утверждения реестра, и новое сведение показывает, какие решения устарели.
- Каждый компонент должен окупаться: измеряем время, стоимость и точность против аналитика и обычного чата и убираем то, что выигрыша не даёт.
