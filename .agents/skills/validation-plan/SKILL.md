# План проверки (stage `validation`)

**Знания:** `kb/methods/E-validation.md` (E1–E9), `kb/methods/C-product-strategy.md` (C6 условия остановки, C8 инкрементальность).
**Лимит:** ≤10 вызовов CLI.

## `deliverables/validation_plan.md` должен содержать
1. **Ожидаемое изменение**: гипотеза «если …, то метрика изменится с X до Y за T, потому что …».
2. **Метрика**: числитель, знаменатель, единица наблюдения (номер/группа/клиент), период, источник данных.
   Разница — в п.п. и в % отдельно (`pp_vs_relative`).
3. **С чем сравниваем**: контрольная группа обычного обслуживания; рандомизация по той единице, внутри которой
   люди влияют друг на друга (семья, владелец, компания) — тогда кластерная выборка: `cluster_sample` с DEFF.
   Анализ «как назначено» (ITT). Если есть более дешёвое плечо — сравнение с ним и честно: хватит ли выборки (`mde_for_n`).
4. **Размер и срок**: n с DEFF [K], темп набора и срок набора + наблюдения [K] (`recruitment`); если не успеваем — что меняем
   (срок, порог, охват) — честно.
5. **Порог решения**, зафиксированный заранее: при каком результате масштабируем / дорабатываем / закрываем.
6. **Нежелательные последствия (ограничители)**: жалобы, отписки, отзыв согласий, ошибки платежей, нагрузка поддержки —
   с порогами остановки и владельцем (роль).
7. **Что не измеряем и почему**; правило «не подглядывать» — промежуточные просмотры только по плану.
≥2 якоря [K] (выборка с DEFF, темп набора). Затем `python st.py check validation` → `stage done validation`.
