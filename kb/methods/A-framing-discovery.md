# A. Постановка проблемы и исследование

## A1. JTBD: switch-интервью и «восстановление одного случая»
- Работа клиента = прогресс, которого человек добивается в конкретных обстоятельствах; демография работу не определяет [З].
- Интервью идёт назад по таймлайну: первая мысль → пассивный поиск → активный поиск → решение → использование. Начинать с последнего момента, когда всё работало (так же в брифе, стр. 4).
- Силы изменения: толчок (push), притяжение (pull), тревога (anxiety), привычка (habit). О силах напрямую не спрашивать, они выводятся из событий.
- Спрашивать про события: где был, кто рядом, что сделал сразу после, «и что было потом?». Мнения и оценки не собирать.
- Респонденты: переключившиеся или почти переключившиеся за последние 30–90 дней; не только довольные клиенты. Паттерны обычно видны после 5–8 интервью, длительность 45–90 минут.
- Для каждого случая зафиксировать: сигнал, кому обратился, что сделал сам, когда решилось, последствие, последний момент, когда оператор мог помочь.
- Если истории клиента нет: написать вопросы и список записей оператора, по которым ход событий восстанавливается.
Источник: https://jobstobedone.org/switch-interview/ [В]

## A2. Opportunity Solution Tree (Тереза Торрес)
- Структура: результат (outcome) → возможности (потребности, боли клиента) → решения → тесты допущений.
- Возможности берутся из интервью, а не из головы; данные поддержки и аналитики служат поводом для интервью, но не «возможностью» сами по себе.
- «Возможность», решаемая единственным способом, это замаскированное решение: спросить «зачем клиенту это» и подняться на уровень потребности.
- Выбирать одну целевую возможность, для неё генерировать минимум 3 решения; тестировать самые рискованные допущения первыми.
- Усилия не использовать для отсева возможностей на этапе оценки возможностей; осуществимость оценивается при сравнении решений.
- Одно дерево = один результат; новое дерево только при смене направления результата.
Источник: https://producttalk.org/opportunity-solution-tree [В]

## A3. Правила Mom Test (интервью без самообмана)
- Говорить о жизни и поведении человека, а не о вашей идее.
- Спрашивать про конкретные прошлые события («когда это было в последний раз?»), а не про гипотетическое будущее и мнения.
- Комплименты, «я бы пользовался» и абстрактные пожелания считать шумом; искать факты и обязательства (время, деньги, репутация).
- Больше слушать, фиксировать цитаты и эмоции; после интервью выписывать выводы отдельно от дословных фактов.
- Модельные (синтетические) респонденты допустимы только для генерации гипотез; спрос и распространённость не доказывают (требование ТЗ).
Источник: https://momtestbook.com/ [В — страница подтверждает существование и тему книги; сами правила из книги, [З]]

## A4. Приоритизация проблем
- Базовая модель RICE: (охват × влияние × уверенность) / усилия; уверенность 100/80/50 %, ниже 50 % считать догадкой; оценки грубые, рейтинг не заменяет суждение.
- Адаптация под бриф (стр. 4): охват = число разных клиентов за период; частота; тяжесть последствий; доля случаев, когда помощь возможна вовремя (addressability). Оценка = охват × частота × тяжесть × addressability × уверенность. [адаптация брифа, не канон RICE]
- Давать диапазоны (мин/база/макс), а не одно число; неизвестный множитель помечать допущением.
- Повторные обращения по одному случаю схлопывать; указывать период подсчёта; учитывать клиентов, которые не обращались (иначе охват занижен).
- Записывать, какой ущерб считается важнее предотвратить и почему (частый вопрос про начисление против редкого длительного перебоя).
Источник: https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/ [В]

## A5. Сигнал против причины; дерево отказов
- Сигнал («близкий не отвечает») не равен причине. Для каждой версии причины указать: какая запись её подтверждает, какое действие оператора из неё следует.
- Fault tree: вершина = нежелательное событие («нет связи у участника»); ниже логические узлы ИЛИ/И и базовые события (нет остатка, ограничение по оплате, устройство выключено, нет покрытия).
- Минимальный набор причин, которых достаточно для вершины, показывает, что устранять первым; веса веток по вероятности и влиянию, а не по размеру на схеме.
- Версии, не меняющие предлагаемое действие, не расщеплять; различать только те, что меняют действие.
- Частоты причин, которых нет в данных: допущение с диапазоном и условием смены приоритета.
Источник: https://support.ptc.com/help/wrr/r12.0.1.0/en/wrr/GettingStartedGuide/Fault_Tree/OverviewFaultTree.html [В]

## A6. Дерево вопросов / issue tree (MECE)
- Тип дерева: диагностическое («почему?») или решающее («как?»); не смешивать в одной ветке.
- Ветки взаимоисключающие и в сумме полные; проверять: можно ли отнести любой факт ровно к одной ветке.
- Пробовать 2–3 разных разреза (например, поток новых клиентов / доля действующих / выбытие номеров), каждый может дать другой вывод.
- Ранжировать ветки по влиянию на исход и управляемости; начинать с «ответа за один день» как рабочей гипотезы и уточнять.
- Для брифа: отставание активных групп = меньше новых × ниже доля действий × раньше выбытие номеров; связь с проблемой, не подтверждённая данными, пометить допущением.
Источники: https://en.wikipedia.org/wiki/Issue_tree [В]; https://www.mckinsey.com/business-functions/strategy-and-corporate-finance/our-insights/how-to-master-the-seven-step-problem-solving-process [В]

## A7. Вопросы, влияющие на решение; ценность информации
- Ценность информации возникает, только когда она снижает неопределённость решения с денежными последствиями.
- План исследования строить от вопросов: «какой ответ изменит решение и при каком значении?»; измерения без такого порога откладывать.
- Для каждого пробела: что не знаем, почему, стоимость получения, порог смены решения, самая короткая проверка.
- Не измерять только то, что легко измерить; дорогие и неизвестные величины часто важнее привычных.
Источник: https://www.oreilly.com/library/view/how-to-measure/9781118836446/c07.xhtml [В — открыт только предпросмотр главы; формулы EVPI из главы не сверены]
